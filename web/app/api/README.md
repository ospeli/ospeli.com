# Ospeli command API

Generated from `core/commands.js` by `scripts/build-commands.mjs`. Do not edit by hand.
The full schemas and examples are in [commands.json](commands.json).

Every action in the app is a named command. The screens call these commands, and so can an agent working for a member of staff.

## Rules for agents
- People decide, Ospeli suggests: an agent may read, and its write commands become proposals that wait for a person.
- A proposal is checked before it is queued: the bed, patient, work order or map must exist and be in a state that allows the action, or the call is refused (not-found or conflict). The same call again returns the proposal already waiting (existing: true). One agent may have one open proposal per command for a bed or work order, and at most 20 proposals waiting in all; 20 is an example setting, not a standard.
- Agent access is off by default, for the hospital and for each ward (ospeli_agents_set_access, people only).
- Only agents on the site's list may call (ospeli_agents_add, people only): each has one role, its wards and an end date of 90 days at most. An agent that is not listed, is past its end date or claims another role is refused. Agents are named, not verified: the browser app has no secret keys; the first version of the site server gives each agent one.
- Anyone on site can stop every agent at once (ospeli_agents_stop_all); only the operations manager or chief operating officer can switch agents on again.
- Agent reads, proposals and refusals made through window.ospeli.run are designed to be recorded in the audit trail with actor type "agent", the agent name and the role it acts for.
- In the browser app these rules are kept by the app's own code and are not a security boundary: a script running in the page can load the app's modules and act as a person, and the trail would then record a person. The first version of the site server (tools/ospeli-server/, run on a site's own computer) checks agent keys and records every call made with a key as that agent, never as a person. A person acts at the server's own window, or from a phone or laptop connected there with a one-time code (recorded as a person in a role from that device, not as a named person); named sign-in is not built yet.
- Nothing leaves the site: commands run on this device or the hospital's own server, never through a cloud relay.

## How to call
- In the browser: `window.ospeli.commands()`, `window.ospeli.describe(name)`, `await window.ospeli.run(name, input, { agent, role })`. Add `dryRun: true` to rehearse a call: every check runs and nothing is read, queued or changed. Any other option is refused (`invalid-input`) and nothing runs.
- Each command has an example input. The ids in it are examples. Where example.needs is present, the example runs only once that is in place (a map exists, a bed is in the named state, a proposal is waiting); the line names the read that finds a real id. An example with no needs line runs as written on the example hospital.
- Command names are ospeli_<module>_<action>. The dotted names used before 12 Nov 2026 still work in this build; each is listed as deprecatedName. The audit trail and the proposal queue always record the new name. Use the new names.
- List reads take a limit and return total and truncated; most take format: "short". Start with the task-shaped reads: ospeli_beds_find_free, ospeli_workorders_list (overdue, locationId) and ospeli_maps_summary.
- A refused call throws an error with .code: invalid-input, unknown-command, forbidden, not-found, conflict or agents-off. agents-off means only that agent access is switched off, for the hospital or for that ward. forbidden covers the rest: a people-only command (a person does it on screen), an agent that is not on the site's list or is past its end date, or a role that cannot run the command. A missing input is read as {}; an input that is not a JSON object is invalid-input. Errors say how to fix the call: a wrong ward, place or map id comes back with the ids you may use.
- Write commands take an optional `expectedState`: if the bed changed since you looked, the command is refused with `conflict` instead of acting on stale data.
- An agent's write returns `{ status: "proposed", proposal: { id } }`. A person accepts or declines it on the bed board (`ospeli_proposals_accept`, `ospeli_proposals_decline`); the agent reads the outcome with `ospeli_proposals_list` (accepted, declined, or expired if the bed changed first).
- More for agents: [/agents.md](../../agents.md) and [/llms.txt](../../llms.txt).
